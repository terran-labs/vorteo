# Live dev mode

Every installation has a delivery mode, and the [installation type](execution-installation.md#installation-type-and-lab-self-updates) decides it. **Stable** installations serve the published static interface (Reliable). **Lab** installations serve the interface from the Expo web dev server running in a persistent source checkout on Host (Live dev), so an edit reaches the owner's open tab through Fast Refresh in seconds. They are one choice because a lab self-update builds from the live checkout: Lab without it could not update itself. Only the owner can change the type, in General settings; the Live development card in Installation controls reports what is served.

Live dev trades provenance for speed. In Reliable mode every served byte traces to a published commit. In Live dev mode the owner's browser runs whatever the live checkout contains right now, including uncommitted edits by Host agents. That code runs on the coordinator's origin with the owner's session, so it can call owner routes, including approvals, without the owner clicking anything. Host agents can already read the owner password file (see [host and container execution](execution-installation.md)), so this is not new capability, but it is a new silent path that removes the publication gate between their edits and the owner's authenticated browser. Metro never receives the owner's cookie or authorization header. Dev container agents cannot write the live checkout: it lives on Host, outside guest-writable mounts, and `promote` accepts only local branches, so Dev work reaches it only after a Host thread chooses to bring it in.

## What serves the interface

The coordinator serves the interface and Installation controls, so live mode lives in the coordinator.

- **State.** The mode is derived from `<stateDir>/installation-type.json`: Lab is Live dev, Stable or a missing record is Reliable, and an unreadable record serves static. A `live-dev.json` written before the merge is ignored. It is owner state, not coordinator configuration, so switching needs no configuration change or restart; the coordinator re-reads it every two seconds and starts or stops the dev server. Owner routes `POST /api/installation/owner/live-dev/query` and `/change` (`{expectedRevision, mode}`) remain for older interfaces: `/change` sets the type to Lab for Live dev or Stable for Reliable, compare-and-set on the type's revision. A stale revision is refused.
- **Paths.** The live checkout is `<host>/live/source`, beside `host/releases`, derived from `deployment.hostReleaseLink`. An installation without that link reports live mode unavailable. The checkout is a Git worktree of the installation's source repository on branch `live/main`, so its commits are visible to Builds without a push.
- **Dev server.** While the mode is Live dev, the coordinator supervises one child: `expo start --web --localhost` in the checkout's `packages/app`, on a loopback port it chooses, with `PASEO_LIVE_PREVIEW_ORIGIN` and `EXPO_PACKAGER_PROXY_URL` set to its `.ts.net` origin. The repository's Expo patch then binds loopback and rejects any Host or Origin other than that origin or loopback. The coordinator writes a pidfile, restarts a crashed child with backoff and logs to `<stateDir>/live-dev/metro.log`. Switching to Reliable stops the child and verifies it exited. The dev server's origin is whichever of the canonical public origin and the recovery origin is a `*.ts.net` HTTPS origin, which the patch requires; an installation whose canonical address is a custom domain keeps its `.ts.net` address as the recovery origin. With neither, live mode reports unavailable.
- **Proxy.** The web UI middleware sends a request to the dev server only when the mode is Live dev, the dev server is ready, the browser holds a valid owner session for this origin, and the browser has not chosen the safe interface. Everyone else gets the static interface. Only GET and HEAD requests pass, and only these: a page navigation, which always fetches Metro's `/` whatever the client asked for; `*.bundle` and `*.map` files; `/assets/`; and the `/hot` WebSocket. Asset paths with encoded characters, backslashes or dot segments are refused, because Metro would normalize them into other routes. No other Metro path is reachable, including the editor launchers (`/open-stack-frame`, `/open-url`, `/_expo/open`), the debugger (`/inspector`, `/json`, `/_expo/debugger`) and `/message`. Proxied responses carry `Cross-Origin-Resource-Policy: same-origin`, because sibling `*.ts.net` hosts count as same-site. The proxied HTML gets the same installation hint injection as the static page. Metro itself still listens on loopback, where any Host process can reach it directly, as with any local dev server. The installation's other address, the custom domain, follows the same rules whether it is the canonical origin or the recovery origin: the coordinator serves the live interface there with that origin in its installation hint, and on its loopback hop to the dev server presents the request as the `.ts.net` origin, the only one the Expo patch admits besides loopback. Metro itself still refuses any other Host or Origin.

## The safe interface

A broken live edit must never lock the owner out of the interface they use to fix it.

- `/?interface=safe` sets a session cookie that serves the static interface for this browser until `/?interface=live` clears it. The static interface is the last release the coordinator installed, which live edits never touch.
- If the dev server answered before but is slow or failing now, the coordinator serves the last page that server returned; the page barely changes, since edits arrive through the bundle and Fast Refresh. Only when there is no such page, because the server is stopped, starting, restarted or has never answered within five seconds, does the page fall back to the static interface, and a one-minute cookie keeps that page's assets static too.
- While the installation is in Live dev mode, every owner page carries a status indicator at lower right: a small circle injected by the coordinator outside the app bundle, so it survives a bundle that fails to compile. The static page server injects it too, so it also appears on the safe interface and on every fallback. Its icon shows the state: live (bolt), the owner's chosen static interface (shield), a slow or starting dev server (clock), or a stopped one (alert). Pressing it opens a panel that explains the state and links to the static interface, back to Live dev, or Installation settings. It uses `<details>` rather than script, and takes the app's floating-panel and status colors from CSS variables, with system colors before the app loads. The sidebar shows no separate Live dev label.
- From the safe interface the owner can switch the installation back to Reliable in Installation settings.

## Changing the live checkout

`node scripts/live-dev.mjs <command>` is the only supported way to change the live checkout's Git state. Each command takes an exclusive lock under `<host>/live/lock`, held for the whole command including any dependency reinstall, and refuses rather than guessing.

- **Tweak.** Agents edit files in the live checkout directly for one-off changes; Fast Refresh shows them immediately. `live-dev claim --by <thread>` records an advisory claim on the files an agent is editing, and `status` shows claims so two agents do not edit the same file at once. `live-dev release --by <thread> [<file>...]` hands back the named files, or the whole claim when no files are given. `live-dev commit --by <thread> -m <message> [--note <line>]` writes a change fragment with the changelog line and inventory review itself, commits it with the claimed edits on `live/main` through the repository hooks, and releases the claim. A refused commit leaves the edits in place.
- **Promote.** `live-dev promote <branch>` merges a local task branch into `live/main`. It refuses remote refs, refuses while anyone's uncommitted edits are present, and checks the merge in memory first, so a conflict never writes markers into the watched tree. The changelog and inventory merge as a union, since release preparations and older commits add entries at the top; change fragments are separate files and need no union.
- **Sync.** `live-dev sync` merges `origin/main` into `live/main` under the same rules.
- **Dependencies.** After each change the command compares the shared dependency cache key, which ignores workspace version bumps, with the key recorded at the last successful install. When it differs, it reinstalls and rebuilds, then asks the coordinator to restart the dev server by writing `<host>/live/restart-request`. Every install, including the first preparation, builds the server stack as well as the app dependencies, because the commit hook typechecks `packages/cli` against the server's built declarations. The coordinator only restarts its own child in response.
- **Version.** After `commit`, `promote`, `sync` and `prepare`, the command writes the gitignored `packages/app/src/utils/live-revision.local.json`: the app version and how many commits the live branch carries past the commit that set it. The sidebar footer reads it through Metro's `require.context` and shows `v<version>+N`, updating through Fast Refresh. `live-dev revision` rewrites it on demand. Uncommitted edits do not count. Static exports never have the file, so Reliable mode shows the plain version.
- **Delivery.** `live/main` reaches GitHub `main` through Builds' usual pull request, the same day. Builds merges `origin/main` back with `live-dev sync` afterwards.

## Fast-track daemon restarts

On an installation whose [type](execution-installation.md#installation-type-and-lab-self-updates) is Lab, daemon, protocol and server changes reach the running installation through a **lab self-update**: a tracked coordinator job that builds the Host daemon and coordinator from the live checkout and switches both to the result. A Stable installation refuses it and keeps installing tagged releases.

- **Build.** The coordinator takes the live checkout's lock, copies the checkout into `<host>/releases/lab-<time>-<id>` with an APFS copy-on-write clone (`cp -c`; a reflink copy on Linux), and releases the lock. Dependencies and the previous build output come along at metadata cost. The clone drops the worktree's `.git` file so nothing in the build can touch the live index. The dependency install runs only when the checkout's dependency key no longer matches the one `live-dev` recorded at its last install. Then `npm run build:server` runs under `nice -n 10`. The web export is skipped: the release receives a clone of the static interface the coordinator serves now, so the safe interface stays the last published one. The release gets the installer's `.installer-release.json` marker with the live HEAD. Logs and the build pidfile are in `<stateDir>/lab-updates/<id>/`. A failed or cancelled build removes the new directory and leaves the running releases selected.
- **Provenance.** The build uses the working tree as it is, including other agents' uncommitted edits. The job records the branch, HEAD and every dirty file with its `live-dev claim` owner, so the owner can see exactly what went live.
- **Host.** The job records the release `host-current` selects, repoints the link, and requests a Host restart in the ordinary restart queue, approved by the Lab type and set to finish current turns where the coordinator supports it. The restart appears in Installation controls with its own status and cancellation. If it fails, the job points `host-current` back at the previous release and requests a restart onto it. If it is cancelled before dispatch, the job only restores the link.
- **Coordinator.** The job then runs the same coordinator-swap handoff as release upgrades: a detached helper repoints `coordinator-current`, restarts the coordinator and restores the previous link if the new one does not answer within two minutes. The restarted coordinator resumes the job from its journal.
- **Rollback.** Every job records the releases it replaced. A request with `rollbackOf: <id>` skips the build and reselects those releases through the same Host restart and coordinator swap. Old `lab-*` releases are removed after a successful job, keeping the selected and previous ones and the newest three.
- **Cancellation.** A job can be cancelled during its build, or while its Host restart still waits in the queue. Once the Host has restarted, use a rollback instead.

## Compatibility

New owner routes and the `liveDev` capability field are additions. Older interfaces never call them and see the static interface. Reliable mode behaves exactly as before. The state file is absent on existing installations, which reads as Reliable. The installation type, lab update routes and the `labSelfUpdate` capability are additions too: an absent `installation-type.json` reads as Stable, which refuses lab self-updates, and a coordinator without them answers 404.
