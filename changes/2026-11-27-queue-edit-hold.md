### Fixes

- A queued message that is open for editing is no longer sent while you edit it. The daemon holds it, and the messages queued behind it, until you save or cancel the edit, for at most two minutes after the editor last checks in, so a closed window cannot block the queue for long. A hold renews for at most 30 minutes; after that the message sends as written once the current hold ends, and the editor shows "This message has been held for editing for 30 minutes, so it will send as written in about 2 minutes. Save your edit now to change it." Other windows show "Being edited" on the message, and the host refuses their edit or send now with "This message is being edited in another window." On an older host that cannot hold messages, opening the editor first warns "This message may be sent as it is while you edit it."

## Maintenance review

Issue #691, part 2 (part 1, the recovery wording, is a separate change). Queue items gain optional `editHold` (`holderId`, `expiresAt`), and queue mutations gain `hold_edit` (acquire or renew, with `expectedRevision` and `holderId`) and `release_edit`, gated on the new `messageQueueEditHold` daemon feature. The store sets expiry two minutes after each renewal, refuses another holder's unexpired hold and send now on a held item with `delivery_conflict`, releases the hold atomically with an edit, keeps the item revision unchanged, and records no receipt or ingress evidence for hold operations. Delivery skips a held head and everything behind it, both before admission and inside the claim, and schedules a wake at expiry; held items are persisted, so a restarted daemon keeps them until expiry. The #680 size refusal is unchanged. The app uses the draft identity as holder, shared by tabs showing the same draft; it acquires before creating the draft, renews every 30 seconds while the editor shows a current queued revision, releases on cancel or close and not on save, sends holds directly rather than through the durable outbox, which is now typed to content operations only, and refuses send now locally on a held item. Tests: one delivery case (held head and the message behind it wait, survive a restarted store, refuse another holder and send now, and deliver after expiry through the scheduled wake) and one draft session case (open sends `hold_edit`; save sends no release); each assertion fails with its fix reverted. The protocol compatibility guide and the recoverable local queue edits inventory entry are updated. README overview and onboarding are unchanged. Not installed: needs a Host and Dev daemon update and interface publication. The queue view test suite mocks the toast context the older-daemon warning uses. After merging part 1, its resend of a rejected edit is typed as a queue change operation.

Review fixes for #697: closing the editor no longer releases the hold, because the draft outlives the editor and other tabs share its holder; only discarding (Cancel) releases, a saved edit releases on the daemon, and a closed editor is covered by the two minute expiry. The renewal loop moved into the draft session (`keepHeld`), whose stop only stops renewing. Holds record optional `heldSince`, kept across the same holder's lapsed holds, and the store refuses renewal 30 minutes after it with `delivery_conflict`; an unreadable or future `heldSince` counts as now. A hold whose expiry lies more than two minutes ahead counts as absent, bounding a backward clock step or corrupted queue file. Send now no longer refuses locally on the client's clock; the daemon decides. Tests: the delivery case is now a table whose endings are expiry, the holder's edit (delivers the edited text) and the renewal cap; the draft session case asserts that stopping renewal sends no `release_edit`.

Second review: the 30 minute start now survives only a gap shorter than one hold period; a hold lapsed longer than that, when the message was free to deliver, starts a fresh window, so a draft reopened hours later on a paused queue can hold again. The cap refusal uses a new mutation error code, `edit_hold_expired`, and the editor stops renewing after it until it is reopened, so a capped edit cannot quietly re-acquire. Hold refusals reach the draft session as typed daemon refusals. Tests: the delivery table adds a long-lapsed hold held again with a fresh start; the draft session case asserts no renewal after the cap refusal. A send now on a held message now reaches the outbox and appears in the rejected-change recovery list rather than a toast.

Independent review: the cap refusal now reaches the editor in production, because the hold send translates daemon refusals into a typed error (the earlier change had put that translation in the queue read instead, which is restored). Holds no longer change the snapshot revision, so pause or reorder from another client is not refused while an editor is open; clients accept snapshots at an equal revision. The upper bound on a hold's expiry allows ten seconds of daemon clock slack, so a small backward step does not release a live hold. Tests: the draft session case translates the refusal through the same helper the hold send uses, and the delivery case reorders at the pre-hold revision while held; both fail with their fix reverted. The recoverable local queue edits inventory entry records that holds leave the queue revision unchanged.
