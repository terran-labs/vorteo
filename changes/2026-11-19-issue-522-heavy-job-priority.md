### Features

- The heavy-job queue orders waiters by a declared priority, then arrival: `run --priority low|normal|high` or `VORTEO_HEAVY_PRIORITY`. A waiter moves up one class per 20 minutes waited, at most to high. A running job is never displaced, and `status` shows each job's priority and its source.

## Maintenance review

First slice of thread-aware heavy-job priority (#522, part of #520): script only. The ticket filename carries the whole order, so copies of the script from before this change, which share the queue directory and sort it by name, agree with new ones. Normal keeps the existing name, so older tickets count as normal; high and a reserved urgent class sort before any arrival time and after the running-job guards; low sorts after. `urgent` is refused from the argument and the environment until the daemon can grant it. A waiter ages by one atomic rename of its own ticket. A reader that finds a listed ticket gone lists again, and a waiter re-reads the queue immediately before claiming, so a promotion or a higher arrival during the memory sample goes first. The atomic slot claim, guards, Builds gate marker and memory guard are unchanged. Priority is recorded on the ticket, not enforced: every caller is the same user. Tests cover the ordering table with an older-format ticket and filename-order equivalence, ageing with an injected clock and a rename during a read, a mixed-version run with a killed high waiter, and the urgent refusal. `scripts/lib/dependency-cache.mjs` is unchanged; a nested install inherits the variable. The inventory entry and development guide are updated. README overview and onboarding are unchanged. Source only; not installed.
