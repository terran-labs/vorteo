### Fixes

- The model list check no longer signs Claude subscription accounts out. Vorteo starts a short Claude Code process to list an account's models and stops it as soon as it answers. Close to the sign-in's eight hour expiry that process also began renewing the sign-in, and stopping it midway discarded the renewed sign-in and signed the account out. Vorteo now skips the check in the last ten minutes before expiry and after it, and reuses the last answer. An ordinary catalog refresh also reuses a fresh answer for ten minutes; a forced refresh still starts a process.
- An account whose access has expired but which can still renew is no longer reported as signed out. Its next agent session starts and renews the sign-in.

## Maintenance review

Claude model discovery (`model-discovery.ts`) reads the account's stored expiry before starting a CLI for a full sign-in account and starts none within ten minutes of expiry or after it; unreadable storage keeps the earlier behavior. Answers are kept per configuration directory, sign-in type, endpoint and command. With no earlier answer, as after a daemon restart close to expiry, discovery reports no models, so discovery-gated models are absent until the sign-in renews and the catalog refreshes. A forced provider refresh skips the ten minute reuse but never the expiry guard, and a failed probe is not kept. `requireFullSignIn` accepts an expired grant that still holds a refresh token; access-only copies still need a live access token. A grant whose refresh token is already spent therefore shows as connected until its next session start fails.

Evidence from the lab Host on 2026-11-13. At the 15:50Z and 16:05Z renewals the first discovery process started after the five minute renewal window opened created the CLI's `.oauth_refresh.lock` at the moment it started (4.7 s and 1.1 s into the window), held connections for about a quarter second and exited without releasing the lock or saving. A controlled CLI 35 to 47 s later waited on that lock, took it over, made one token request and was rejected with a spent refresh token; the access token was revoked and the CLI erased the stored sign-in. The discovery process just before each window took no lock. The earlier 7.8 s delay before a controlled CLI's token request was that wait on a stale lock, not the CLI's own start time. The daemon started a discovery process per account about every five seconds; what forces the catalog that often is not traced, and this change does not reduce forced refreshes.

Other short-lived CLI starts for a full sign-in account are unchanged and remain open: internal one-shot sessions (titles, branch names, git metadata) are closed seconds after they answer, though they need the renewed token before they can answer, and the provider diagnostic runs `claude auth status` with a five second limit on request. Focused tests cover the expiry guard with and without an earlier answer under a forced refresh, and the expired renewable grant against an access-only copy. The subscription accounts entry in the customizations inventory records the guard and its empty-answer limit. README overview and onboarding are unchanged. Not installed; acceptance needs both accounts to renew unattended through three consecutive expiry windows with no discovery process started inside the guard.
