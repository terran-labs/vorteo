### Fixes

- Host release cleanup has a switch, the `hostReleaseCleanup` coordinator setting, and defaults to a dry run: after each Host install it records which old releases it would remove and why every other release stays, and removes nothing until the setting is `on`.

## Maintenance review

Builds asked for a way to see the first delete list before anything is removed. `hostReleaseCleanup` accepts `off`, `dry-run` and `on`, is registered for `request-coordinator-settings` as a display-safe plain key, and refuses any other value. A dry run reads the same evidence as a real run, takes no lock and renames nothing, and writes the plan (folders it would remove, copies and unfinished deletions it would finish, and each reason a folder stays), the mode, the keep count and any error to the job's `retention.json`. It also records link history, outside the release root, so the first real run has one; a failure there is recorded and never fails the install. A real run records the same plan before deleting. To enable: read `plan.remove` and `plan.kept` in the latest `retention.json`, then request `{"hostReleaseCleanup": "on"}` with `node scripts/installation-agent.mjs request-coordinator-settings --file <patch>`. Turning it on is a coordinator settings change, approved in Installation controls or under the owner's maintenance delegation, and whoever approves it must first read the latest dry-run list in `retention.json`. A coordinator older than this change refuses a `coordinator.json` that sets `hostReleaseCleanup` or `hostReleaseKeepNewest`, so remove both before rolling the coordinator back past it. Tests cover each mode, the default, an invalid value, a dry run leaving the tree unchanged and listing exactly what a real run then removes, and a dry run whose evidence fails without failing the install. README overview and onboarding are unchanged. Not installed.
