### Fixes

- Hosted Claude agents now run the Claude Code bundled with the installed release instead of whatever `claude` is on the Host's PATH, so models such as Fable 5.2 no longer fail with an unsupported-version error after the session host starts.
- Starting a Claude agent now refuses, before the CLI launches, a model that the Claude Code it would run is too old for, and names that executable, its version and how to update it.
- Fable 5.2 requires Claude Code 2.1.290, the version Claude Code itself reports, instead of 2.1.321.
- Managed Host source-update background release cleanup is suspended until startup and pruning share exclusive lifetime protection. Successful installs retain old releases and record the reason in their background cleanup receipt.

## Maintenance review

The session host never initialized the managed Claude CLI selection that daemon workers receive from the supervisor, so every hosted Claude agent launched PATH `claude`. On this Host that was Homebrew's 2.1.285, which refuses Fable 5.2. The host now selects the release's validated CLI when its launchd job starts it through the release link and logs the selection at startup; a source checkout or test harness keeps PATH `claude`, and explicit command overrides are unchanged. A failed packaged-CLI validation still refuses launches instead of falling back, as before. Each launch now checks the requested model's Claude Code floor against the executable it will run, probing and caching that executable's version, so a shared profile or another process can no longer bypass the catalog's gate. Executables whose version probe fails or times out are cached as unknown until the file changes, so a hanging wrapper costs one timeout instead of one per launch. The host publishes its canonical release directory to `session-host/release.json` only after acquiring its exclusive lock. The receipt binds that actual lock inode generation and holder; a failed second start cannot replace it. Release inspection refuses missing, invalid, unreadable or stale evidence. Older hosts can keep running without the new receipt; this does not authorize cleanup of an unknown release. Receipt write failures warn without preventing host startup. The durable sessions entry is updated. Validation covers real filesystem receipt failures and lock replacement, safe release retention, failed-probe caching, selected existing host-service cases and normal checks; independent review remains required. Delivery needs a session-host restart through the tracked lifecycle workflow; a daemon restart alone does not reload the host. README overview and onboarding are unchanged. Not installed.

Retention review correction: cleanup validates bounded private lock contents, an exact decimal PID and the matching receipt generation before checking process absence. Missing lock evidence beside any retained receipt skips cleanup, including after a released lock; stale releases can remain until a verified replacement publishes fresh evidence. This snapshot check does not exclude a concurrent host start during asynchronous pruning. A shared lifetime protocol remains unimplemented; the explicit suspension below protects this background cleanup path instead.

Background cleanup suspension: the source-update installer no longer invokes release-folder deletion from its post-install background path, even when lock and receipt files appear absent or valid. The successful install result reports suspension and points to its retention receipt. Other cleanup and the generic pruner are unchanged. Retained releases accumulate and can leave insufficient disk space for future builds or installs until separately authorized safe cleanup becomes available. This does not restore already missing files or authorize a host replacement. The shared lifetime protocol remains unimplemented.
