### Fixes

- Vorteo no longer ends a full sign-in Claude account's Claude Code process in the middle of a sign-in renewal when the renewal finishes within two and a half seconds. Claude Code holds a lock while it renews, and a process stopped inside that time can discard the renewed sign-in and sign the account out. Session close, idle cleanup, session host shutdown, a restarted query and Vorteo's short internal sessions now wait for that lock first. This path had not been seen to cause a sign-out.

## Maintenance review

The wait applies only to full sign-in accounts, the same scope as the discovery expiry guard. For every other session `waitForClaudeRenewal` resolves without touching the file system, so process teardown is not preceded by a file read; a first version checked the lock for every session and failed four existing close tests in `agent.runtime-exit.test.ts`, which expect the stop signal as soon as close begins. For a full sign-in account the check necessarily precedes the stop and costs one file read when no renewal is running. `claudeRenewalInProgress` and `waitForClaudeRenewal` in the Claude provider's `account-starts.ts` read the modification time of the `.oauth_refresh.lock` directory in the account's configuration directory. Claude Code 2.1.321 takes that lock before it sends the renewal token, touches it every five seconds and releases it after saving, so a lock not touched for twelve seconds is treated as abandoned and cannot delay later stops. The whole wait is raced against a timer so a file system that stops answering cannot hold a stop. `closeSession`, the query retire path, the missing resumed conversation path, the query pump's exit and the model discovery probe wait before ending the CLI; the session host's idle close and shutdown are covered because both end a session through its close. The pump waits because leaving it makes the SDK end the process, and the discovery probe hands the SDK its own abort controller, aborted after the wait, because the SDK ends the process as soon as its controller aborts. The retire path waits before it detaches the query so no second CLI starts beside the first; the missing resumed conversation path detaches the child and keeps its handles before it waits, so an exit during the wait is not reported as a crash. The wait is two and a half seconds so that the wait, one poll and the two second grace before a forced kill fit the daemon's five second agent close limit; in the session host, a ten second settle wait, the wait and a four second kill stay inside its twenty second shutdown deadline. Observed renewals held the lock for 0.6 to 6 seconds on the lab Host on 2026-11-13 and 2026-11-14, so the slowest observed renewal is longer than the wait. Not covered: a renewal slower than the wait, which logs a warning; a renewal that starts after the check, during the grace before a forced kill; a Claude Code login outside a Vorteo full sign-in account, such as the machine's own login or a custom provider's configuration directory, which gets no wait; `claude auth status` stopped by its five second limit outside the expiry guard; sign-in flows stopped by their own limits; a process killed from outside Vorteo; the SDK's exit hook and the supervisor's forced kill when the daemon or session host exits with a CLI still alive; and a later Claude Code that renames the lock, which would silently disable the wait. About ten renewal rounds across at least twelve daemon and five session host restarts lost no sign-in before this change, with restarts kept away from renewal times by hand. One test covers the wait, its bound, the exemption for other sign-in modes, a session close held by a live lock, and the abandoned lock; it fails when the wait is removed from the session close. The discovery probe's abort change has no dedicated test. The subscription accounts entry in the customizations inventory is updated; that entry appears twice in the inventory after an earlier merge and only the current copy was edited. README overview and onboarding are unchanged. Not installed.
